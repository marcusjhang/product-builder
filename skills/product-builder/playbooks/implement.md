### Implement

**You own the build. One slice at a time, tests from the acceptance lines, verified on the surface, reviewed, one PR each.** Delegate independent slices to implementer subagents when asked or under context pressure (the mode's Subagents section); review every diff yourself.

Preconditions: status Ready to implement with a green Definition of Ready, or an explicit user override recorded in the ledger; a worktree off main; if main moved since the baseline, `playbooks/revise.md` delta first.

One PR. When the appetite or the user says one PR and the plan has slices, the slices are ordered commits on one branch `<slug>/p1-<verb>`: steps 1 to 6 run per commit with one implementation-log row and one restated contract per commit, and steps 7 to 9 run once at the end for the branch. This is a supported shape, not an exception; the reply says "one PR, n commits" in its first line. If the plan folder is untracked, commit it first as its own commit (`docs(plans): <slug> plan`) on the slice branch so the PR body's link resolves; this is not scope drift.

Per slice:

1. Re-read `decisions.md` (implementation log) and the slice block. A slice already logged as opened or merged is never redone.
2. Restate the contract in the reply: stories and acceptance lines, depends-on, size, files, data, flag, tests to write (one per acceptance line, named), live check, regression, rollback. Commits stacked inside a PR are restated the same way, one contract per commit; the first compile failure that needs a file from a later commit is friction (step 4 and `playbooks/revise.md`), never a silent fold of one commit into another. If a dependency PR is not merged, stack on its branch. If the contract cannot be written because its target does not exist or its premise is false, stop: one question with the options (nothing to do; a different target; a plan), and no ledger row until the user answers.
3. Branch `<slug>/p<n>-<verb>`, and write the slice's implementation-log row (branch, status `started`, last step `branch`) before the first commit; update its `Last step` at every step below so a dropped session resumes from the row.
4. Build. P1 with a flag is the walking skeleton: declare the flag (default off), the thinnest end-to-end path, the instrumentation event, nothing else. When a skeleton commit exists only to run a live check and no driver is reachable, fold it into the next commit and record the unrun check as an ASSUMED row; do not write code twice for a check that cannot run. Write the failing tests from the acceptance lines first where a seam exists; implement with the reuse ladder (invoke a minimal-implementation skill when the profile names one); stay inside the changes table. Budget rule: if the slice grows past twice its size estimate or needs a file outside its list, stop and run `playbooks/revise.md` (friction) to split or re-plan.
5. Verify: the profile's check and test commands, run once by you while iterating and once more through the profile's verification agent, when one exists, only at the end of the slice as the certifying run; **product-builder-verify** on the matching surface with the flag on and off; the regression lane; for a schema-expand slice, the migration replayed on a scratch database. No pass is claimed unless the command ran in this reply and its output is shown.
6. Review: **product-builder-review** with the slice contract. Both verdicts required (spec compliance, quality). Fix loop of at most three rounds, and every fix commit goes through the review skill's fix wave before its finding closes; a round that closes findings without waves has not run. Findings that change locked copy, add an analytics property, or cannot be verified here are not asked mid-slice; they are listed in the end-of-slice reply under "your call" with the recommendation, so a slice has one stop, the menu.
7. `playbooks/opening-a-pr.md`. The body links the plan folder and stories, includes numbered steps a human can follow to see the change, and before/after screenshots or a recording for a UI slice, per the profile's Evidence section.
8. Ledger: implementation-log row; tick the slice in `implementation.md`; `Verified by: <test name>` on the stories.
9. End-of-slice menu: the reply carries the PR title and body inline (the user sees the body before anything opens), then any fact that blocks opening as its own line above the menu (an untracked plan folder, a baseline-red check), then the menu: open the PR (default), keep the branch, or discard (only on an explicit request, confirmed by the typed word `discard`). Merge is the user's (G8). Remove worktrees the suite created once their PR is merged; never force-delete uncommitted work. Then the next slice whose dependencies are merged.

`--parallel N`: independent slices (no shared files, no unmerged dependency) go to implementer subagents in isolated worktrees, at most N in flight; each gets only its contract, the change table for its files, and the interfaces from merged slices, and returns DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT, or BLOCKED with a report. You run steps 5 to 8 on each returned diff. The ledger is the queue; a slice is claimed by writing its row before dispatch.

Autonomy: proceed on reversible work; stop for merge, push to shared branches, migrations against shared databases, deletes, external messages, production flag flips.

**Reply, per slice:** for the user of the feature, what works now; for the next engineer, what the slice owns; the tests and their output; the live evidence with the flag on and off; the review verdicts and what was fixed; the PR URL; deviations and the revision they triggered; the next slice.
