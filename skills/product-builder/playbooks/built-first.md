### Built first

**You own the plan the code implies. Derive it, confirm it, cast the panels, prove it on the surface, hand off.** For code that exists before a plan: a finished branch, an open PR, a teammate's PR, a diff pasted in. Review alone is not a plan; a panel with nothing to read against finds only what the diff shows it.

1. Intake. Baseline per the profile's rule. The diff (`git diff <base>...<head>`, or the PR), its commits, its PR body, and any tracker text. The intake probe from `playbooks/plan.md` step 1 runs on the diff's nouns: what already ships on `origin/<default>` that this duplicates, the closest existing feature, prior plan folders on the area. Say whether the work is the user's own or a teammate's, because rulings on a teammate's PR become comments, never edits.
2. Derive the plan into `docs/plans/<slug>/`, status `Derived`, `Source: <branch or PR>` in the header. `product.md`: the problem and the audience as the PR body and commits state them; user stories with WHEN/THEN acceptance read from the tests and the surfaces touched, one per behaviour the diff adds; non-goals from what the diff visibly stops short of; instrumentation and rollout from what the diff contains. `implementation.md`: the changes table from `git diff --stat` and the symbols touched, data and contracts from the schema and types touched, the test strategy from the tests present. Every line the diff does not settle is a row marked `ASSUMED: derived from the diff` in `decisions.md`; never invent a number, a name, or a reason. Size from the diff (files, subsystems, surfaces), stated.
3. Confirm with the author, once: the ASSUMED rows as one multi-select, at most four per question, and the stories as one block. A story the author rejects is deleted, not argued. For a teammate's PR with no author in the session, the rows stay ASSUMED and the reply says so.
4. Round trip. For every value the diff writes (a field, a filter, a setting, a flag, a record), name the screen or endpoint that displays it and the control that removes it, read from the code. A value with no display or no removal is a finding at act on before any panel runs.
5. Panels. **product-builder-pm** on the derived `product.md`, where the customer voice and the designer are the seats that matter; **product-builder-techlead** on the derived `implementation.md` against the code at the head, with the cost seat when the diff calls a model or a metered API; **product-builder-review** on the diff with `--contract` pointing at the derived stories. Findings from all three land in one block and one rulings table.
6. Verify. **product-builder-verify** on the matching surface, flag on and off; the regression lane with CI's exact configuration.
7. Personas, when a UI surface changed: **product-builder-personas** in live mode against a preview or local target with the derived stories; paper mode when no driver is reachable, said in one line.
8. Definition of Ready, read backwards. Print the list with evidence per box; a red box is a gap the code shipped with, named as such, not a reason to stop. Then the Definition of Done items that apply before merge.
9. Hand off. Own work: fixes as commits on the branch, each through the review skill's fix wave, then `playbooks/babysit.md` for merge-ready, then QA and Ship from the derived plan. A teammate's PR: the findings block as review comments, posted only on request, with the derived stories linked as the reviewer's reading of the intent.

**Reply:** the source and the size; the derived plan path with the ASSUMED count; the round-trip table; one findings block across the three panels with counts; verification per scenario; the Definition of Ready with red boxes named as shipped gaps; the next move.
