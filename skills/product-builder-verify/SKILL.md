# product-builder-verify

1. Read `.product-builder/drive.md`: launch command, readiness signal, login or seed, selectors, flag flip, teardown. When an installed browser-testing skill provides a server-lifecycle helper and headless-browser conventions, use it instead of hand-rolling them. When `drive.md` was never validated (setup skipped the launch, or a field reads `UNKNOWN`), this first run validates it and writes the outcome back. When the app's login page proxies to another host, do not follow it; mint a session per the repo's documented recipe and set it as a cookie in the driver, and record the recipe in `drive.md`. A credential that fails (a rotated database password, a key that answers 401) is a friction event: name it in one line, list the local alternatives you detected (a scratch clone of a local database, the preview environment the profile names, a mock), ask one question with the cheapest real path recommended, and record the answer in the ledger. A mock that would ship in the product is the user's call and is challenged by the review; the preview environment, when one exists, is preferred over it.
2. Pick the surface by what changed: UI → the browser driver in the profile; CLI → run it; API → a real request with the real client; migration → replay on a scratch database; job → trigger it and read the side effect back.
3. For each scenario: the click path or command, the observable result, the pass predicate, and the flag state. Write them down before driving.
4. Drive it. Capture evidence to the scratchpad first, then move what a claim will cite to its home per the profile's Evidence section: text (response bodies, log lines, exit codes, command transcripts) to `docs/plans/<slug>/evidence/<slice>-<scenario>.txt`, screenshots and recordings per the profile's Evidence section (by default screenshots committed under `docs/plans/<slug>/evidence/` within its size cap and recordings linked, never committed; or the artifact store it names). The reply and the ledger cite the durable path, never the scratchpad. Run the command in this reply; a pass claimed from an earlier run is not a pass.
5. Regression lane, whenever tests exist: the profile's test command with CI's exact lane configuration (runner flags, pool, isolation, order, shards, as the profile's Stack and commands records them from the CI config), never a changed-files selection alone. A test that reads a changed file by path (a fixture, a snapshot of a generated file, a contract test over source text) has no import edge, so a changed-files run cannot see it: grep the test tree for every changed path by name and run every hit. On trunk when the scenario is load-bearing and trunk has the feature: the same scenario at the base, compared.
6. No driver reachable → say so in one line, run what can be run (commands, requests), and mark the UI scenarios "not verified, no driver" rather than inferring.

**Reply:** per scenario: pass or fail, the evidence path or output, the flag state. "Inconclusive" is a fail and says why.
