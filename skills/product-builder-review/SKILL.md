name: product-builder-review
description: Reviews a diff (branch, PR, or working tree) with read-only reviewer subagents cast by what the diff touches (always a staff simplicity hawk, a QA engineer, and a product owner; then every seat whose signal the diff carries: database, security, frontend, SRE, integration, cost, accessibility, adversarial user, silent-failure hunter, backwards compatibility, prompt quality; a wide diff runs them in waves of five), each with the stated intent of the change. Merges findings into act on / consider / noted / dismissed with attribution and a confidence score, runs a verifier that re-checks every critical and high against the code, names the one fact a risky diff is safe because of and proves it by running real code, re-reviews every fix commit with a three-seat fix wave before its finding closes, and with a slice contract returns two verdicts: spec compliance against the acceptance lines, and quality, plus deviations from the plan. Use for "review this", "tear this apart", "find blind spots", or from the implement, built-first, bug-fix, refactoring, perf-issue, and babysit playbooks.
argument-hint: [--diff base..head | --pr N] [--contract path] [--fix-wave <finding>]

# product-builder-review

Never edits code. Read `.product-builder/learnings.md` first.

1. Scope and intent: the diff (`git diff <base>...HEAD`, a PR, or the working tree); the intent from the task, the PR body, the commits, then the diff. State the intent in two sentences; every reviewer receives it verbatim.
2. Cast by signal, with a reason per seat. The count follows the diff, not a cap: a small diff casts the three always-seats and perhaps one more; a diff that carries many signals casts every seat whose signal it carries, dispatched in waves of at most five so no seat is dropped for size, and the reply lists the seats cast and the signals that cast them. A seat whose signal is present and which was not cast is a review defect. Always: staff engineer (simplicity, DRY, YAGNI, divergence from existing patterns), QA engineer (are the tests meaningful, edge cases, and can each test fail on the behaviour it names: a synthetic click that fires no mousedown before a focus assertion, a mocked subject, an assertion with no literal value, is a finding, not coverage), product owner (does the change serve the stated intent, scope creep). By signal: database or migration, security, frontend, SRE or resilience, integration, accessibility, adversarial user; a silent-failure hunter whenever the diff touches error handling, retries, or async code; backwards compatibility whenever the diff touches a public contract, a shared helper, a fixture, a snapshot, or a file that an existing test reads by path rather than by import (the seat runs the tests that name the changed paths, not only the tests that import them); prompt quality whenever the diff adds or edits text a model reads (a prompt, a question, a criterion, a system message), where the seat reads the text as the model would, predicts the answer for eight to twelve canonical inputs including the edge each criterion names, and flags an instruction that contradicts its own criterion or another instruction; cost whenever the diff adds or changes a call to a model or a metered API, where the seat measures the worst-case request (characters, tokens, share of the model's window, price per call) with maximum-length inputs and reports whether a size assertion exists in the tests. The profile's reviewers-by-path are mandatory seats when their paths are touched.
3. Dispatch in parallel, read-only, self-contained prompts: the intent, the list of changed files with the base and head refs (never the raw diff when it is over 300 lines) and an instruction to read them, the seat's mandate, and the output schema (severity, confidence 0-100, file:line, the concrete failure scenario, the suggested change; at most 40 lines; pointers, not payloads).
4. Verifier pass by you: re-check every critical and high against the code; drop what does not survive. Below 60 confidence lands in noted. When the profile names a judge, first run its `finding` gate over every returned finding through `${CLAUDE_SKILL_DIR}/../product-builder/scripts/judge` (`--batch`; state per finding: the finding and the hunk or section it names, verbatim) and `finding-pair` over findings that name the same file; in `gate` mode the judge's bucket and confidence replace the seat's self-reported ones and your re-check covers what it leaves in act on or consider, in `shadow` mode its buckets are logged beside yours and yours stand. For a diff that touches shared code, name the one fact it is safe because of and prove it with a script or test that runs the real code; if you cannot prove it cheaply, mark it unproven.
5. One block, at most eight lines, grouped by bucket with seat and confidence; an agreement map in one line; the rest counted, dismissed with reasons.
6. With `--contract`: the spec-compliance verdict (each acceptance line: covered by a named test or live check, or not) and the quality verdict, both required; deviations from the plan's change table named for the Revise playbook. When the profile names a judge, run its `spec-line` gate per acceptance line with the named test's source (`--batch`); in `gate` mode a line the judge marks uncovered is uncovered in the verdict unless you quote the assertion that covers it, in `shadow` mode the verdict is logged beside yours.
7. Fix wave. After any fix commit that answers a finding, a wave of three seats on the fix diff only (`git diff <finding-sha>...<fix-sha>`), before the finding closes: the verifier, the seat that found it, and one adjacent seat chosen by what the fix touched. Fixes move boundaries: a narrowed catch changes which errors reach the user, a changed close order changes what a second click does, a renamed label changes what a derived string contains, a cap truncates something new. The wave's findings enter the same block and the same ledger; a finding closed without a wave is still open. `--fix-wave <finding>` runs this step alone.
8. Rulings: apply what the contract allows; hand the rest back to the calling playbook as a "your call" list with recommendations rather than asking here, unless the review was invoked directly by the user, in which case one multi-select over the act-on and consider items, at most four per question. When a plan exists, ledger rows per the mode's Subagents rule: one row per finding, every bucket, counts equal to the block, written before the reply.

**Reply:** the intent; the cast; the findings block; the safety fact and its proof or "unproven"; with a contract, both verdicts and the deviations; per fix wave, the fix, its three seats, and what they found; what needs the user.
